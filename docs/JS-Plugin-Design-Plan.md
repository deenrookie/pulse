# Pulse JS Plugin 优化方案

日期：2026-09-14  
状态：设计提案，尚未实现  
范围：Extensions 中的 JS Plugins；Match & Replace 仅保留必要联动与可靠性修正。

阅读导航：产品目标与现状见第 1–3 节；SDK 和开发自由度见第 4–7 节；前端设计见第 8 节；运行时与工程化见第 9–11 节；实施与验收见第 12–13 节。

| 阶段 | 核心交付 | 解决的问题 |
| --- | --- | --- |
| R0 | 可靠编辑、保存与运行版本、诊断和取消 | 放心修改，失败可恢复 |
| R1 | 报文 SDK、配置、状态、真实样本测试与工作区 | 少写重复代码，日常任务好完成 |
| R2 | 主动 HTTP、手动 Action、Mock、后台分析 | 从改包脚本扩展成实用工具 |
| R3 | 多文件、依赖打包、自定义 UI、本地资源 | 复杂插件可维护，开发者可自行扩展 |

## 1. 目标与设计结论

将 Pulse JS Plugin 从“能改请求和响应的脚本”升级为“开发者可以编写、测试、配置和复用的本地扩展工具”。

优化目标是三个方面：

1. **更加好用**：从真实流量创建插件和测试样本；编辑、调试、启用、定位错误都在同一工作区完成。
2. **更加实用**：直接覆盖鉴权、签名、解密、Mock、响应分析、批量处理等真实任务，减少重复编写 Header、URL、编码等基础代码。
3. **更大的自由度**：保留直接修改报文的能力，逐步开放跨请求状态、主动 HTTP 请求、手动动作、多文件与依赖打包、自定义 UI 和本地资源能力。

推荐同时保留两个开发入口：

- **快速脚本**：一个 `.js` 文件即可运行，支持浏览器内编辑，不要求 manifest、npm 或构建工具。
- **插件项目**：需要拆文件、类型提示、依赖打包、测试用例和 UI 时，再升级为目录形式。

两者共享同一套宿主 API 和测试机制。开发者不应为了多加一个 Header 被迫创建完整插件工程，也不应因为最初使用单文件就无法继续扩展。

本文中的 API、接口路径、组件拆分和版本阶段均为**拟议设计**，不能直接当作当前 SDK 使用。确定采用后，应先冻结最小 API 契约，再实现并生成开发文档。

## 2. 当前项目事实与问题

### 2.1 已有基础

当前后端使用 goja；JS 插件通过全局 `plugin` 元数据、`onRequest(ctx)`、`onResponse(ctx)` 工作。每次钩子调用使用新的 VM，插件按文件名排序执行。

当前已经提供：

- 在线 CodeMirror 源码编辑与 JSON 测试输入。
- Check 编译/加载校验、Test run 沙箱试跑。
- 保存文件并热加载、启停、删除、目录配置。
- 插件样例、最近 60 行日志、成功调用计数。
- `pulse.log()` 与 `pulse.version`。

当前请求执行顺序：

```text
客户端请求 → onRequest → 请求重写 → 请求拦截 → 上游
上游响应   → onResponse → 响应重写 → 响应拦截 → 客户端
```

Repeater 默认绕过插件与重写；插件没有可供脚本使用的网络、持久状态和文件 API。当前协议升级路径会提前进入隧道流程，不能假设普通响应钩子也覆盖 WebSocket 握手或帧。

### 2.2 体验与能力差距

| Before：当前情况 | After：目标设计 | Why：用户收益 |
| --- | --- | --- |
| 操作 Header 要遍历数组，样例重复实现 URL、Query 工具 | 提供稳定的 Header、URL、Cookie、Body、编码 API，同时保留原始数据 | 把精力放在插件逻辑上 |
| 每次新 VM，无法自然保留 Token、计数器、缓存 | 明确提供事务上下文、内存状态、持久存储 | 支持鉴权、签名、会话关联和去重 |
| 只能被动修改经过代理的流量 | 增加手动动作、主动请求、完成后分析 | 插件成为可主动使用的工具 |
| 测试要手写 JSON | 从 Flow、Repeater、raw 报文导入，保存多组用例 | 测试真实场景的成本更低 |
| 保存直接影响运行版本 | 编辑源文件、运行版本分离；成功校验后应用 | 可以自由试验而不破坏正在工作的插件 |
| 编辑、样例、插件列表分散 | 插件列表 + 详情工作区，测试和日志围绕当前插件组织 | 降低导航成本 |
| 错误只有字符串与日志尾部 | 错误行列、执行记录、输入输出 Diff、关联 Flow | 能回答“为什么没有生效” |
| 文件名决定顺序 | UI 显示并配置执行顺序 | 无需用重命名管理业务关系 |
| 配置值写死在源码 | 元数据声明配置表单，源码与用户设置分离 | 分享、切换环境和复用更容易 |
| 日志全部展开，刷新失败被忽略 | 列表显示健康摘要，详情按需加载记录；失败显示过期状态 | 插件增加后仍然可管理 |

### 2.3 先处理的可靠性问题

这些问题来自当前代码审查，不应被包装成尚未复现的运行测试结论：

1. **超时未覆盖顶层执行**：`compile()` 与 `runHook()` 中的 `RunProgram` 没有处于现有钩子超时计时器的保护范围内。应覆盖初始化和调用，并让宿主 I/O 也能取消。
2. **保存提示与启用状态不一致**：成功分支直接提示 `saved and active`，但原有停用状态可能仍然保留。应以服务端返回的加载与启用状态展示。
3. **草稿容易丢失**：源码只保存在组件状态，离开 Extensions 会卸载；加载另一个插件或样例可覆盖草稿。测试输入在切换编辑子页时也可能重置。
4. **旧结果没有版本归属**：代码或样本改变后，原来的 Check/Test 结果仍可能显示为有效成功。
5. **编辑器没有配置完整撤销历史**：当前没有注册 CodeMirror `history()`；应补齐并验证撤销、重做与切换文件后的行为。
6. **可写字段与文档不完全一致**：文档称响应阶段的 request 为只读，但当前 `runHook()` 仍会回写 request；部分导出字段如 `httpVersion`、响应 `reason` 又未被回写。需要明确契约、适配旧版本并覆盖测试。
7. **计数与错误语义混在一起**：`Hits` 在成功执行时才增加；后续成功会清空最后错误字段。应分别记录尝试、成功、修改、错误和超时，不丢失历史错误。
8. **启停持久化失败没有被可靠反馈**：当前 `SetEnabled` 忽略保存错误。应把“内存已切换但磁盘未保存”变成明确失败处理，而非成功提示。

关联修正：Match & Replace 的 `Open()` 读取已有规则后没有重建正则缓存，需补充重启后正则仍生效的回归用例；不在本方案中展开规则页完整改版。

## 3. 用真实任务确定能力优先级

| 任务 | 开发者应如何完成 | 依赖能力 | 阶段 |
| --- | --- | --- | --- |
| 只给目标 API 添加鉴权头 | 选择目标、配置 Token、调用 Header API | 配置、范围、报文助手 | R1 |
| 从登录响应取 Token，用于后续请求 | JSON 读取后存入插件状态，后续读取并写 Header | JSON、状态、请求响应关联 | R1 |
| 请求签名与响应解密 | 使用明确的字节/编码/密码学函数处理数据 | Byte Body、编码、哈希/HMAC，后续加解密 | R1 / R2 |
| Token 过期后主动刷新 | 缓存判断、单次刷新、主动请求、复用结果 | 异步 HTTP、带键合并的任务协调 | R2 |
| 调试接口尚未实现 | 匹配请求后返回本地 JSON 响应 | `ctx.respond()` | R2 |
| 从选中请求生成专用格式 | 在右键菜单执行动作，查看/复制输出 | Action、结果面板 | R2 |
| 批量分析已抓取流量 | 筛选历史、分批处理、输出发现结果 | 只读查询、后台任务、结果表格 | R2 / R3 |
| 自定义解密查看器 | 插件输出结构化结果，后续注册自定义面板 | 结果展示、UI 扩展桥接 | R2 / R3 |
| 使用已有纯 JS 算法库 | 本地安装依赖、打包为插件产物并加载 | 多文件、构建契约、兼容性检查 | R3 |
| 使用本地字典或外部分析工具 | 读取授权目录，必要时调用可信本地进程 | Files API、独立执行进程 | R3 进阶项 |

“更大的自由度”以这些可完成的任务衡量，不以 API 数量衡量。

## 4. 插件编程模型与兼容策略

### 4.1 保留现有写法

旧插件继续支持：

```js
plugin = { name: "Add Header", version: "1.0" };

function onRequest(ctx) {
  ctx.request.headers.push({ name: "X-Test", value: "pulse" });
}
```

不要强制把所有插件改成类、注册器或完整项目。新 SDK 使用 `apiVersion: 2` 显式选择新语义；未声明的插件按旧版契约处理。

### 4.2 建议的 v2 单文件示例

以下仅用于说明 R1 目标，不是当前可运行代码：

```js
plugin = {
  id: "local.auth-header",
  name: "Auth Header",
  version: "1.0.0",
  apiVersion: 2,
  description: "为目标 API 注入测试凭证",
  config: {
    token: { type: "secret", label: "Access token", required: true },
    prefix: { type: "string", label: "认证前缀", default: "Bearer" }
  }
};

function onRequest(ctx) {
  if (!ctx.config.token) return;
  pulse.headers.set(
    ctx.request,
    "Authorization",
    ctx.config.prefix + " " + ctx.config.token
  );
  pulse.log.info("已写入认证头", { flowId: ctx.flowId });
}
```

执行范围由插件详情中的 Execution 配置管理；脚本仍可使用任意条件逻辑进一步筛选。运行时按“用户选择的范围 AND 脚本条件”执行。

### 4.3 元数据与稳定身份

- `name`、`description`、`version`、`author`、`homepage`：展示与分享。
- `apiVersion`：SDK 语义版本，不用插件自身版本代替。
- `id`：关联配置、状态、执行记录和修订；单文件用户可由宿主首次导入时生成并持久化，无需强制手写。
- 源文件重命名不应导致 Token 配置、状态和历史全部丢失。
- 重复 `id` 导入时，显示“更新现有插件 / 安装副本”；副本使用新身份，不直接覆盖。
- 目录切换后，不应仅按相同文件名把旧目录的密钥和能力授权转移给另一个插件。

## 5. 实用 SDK 设计

### 5.1 报文与数据助手（R1）

| API 草案 | 约定 |
| --- | --- |
| `pulse.headers.get(message, name)` | 大小写不敏感，返回首个匹配值；不存在返回 `null` |
| `pulse.headers.getAll(message, name)` | 返回所有匹配值，保留顺序 |
| `pulse.headers.set(message, name, value)` | 在第一个原位置设置，移除其余同名头；不存在则追加 |
| `pulse.headers.append(message, name, value)` | 追加一条，适用于需要重复的头 |
| `pulse.headers.remove(message, name)` | 删除全部同名头，并返回删除数量 |
| `pulse.url.parse(url)` | 标准化解析 scheme、host、port、path、query；不可用简单字符串切割替代 |
| `pulse.query.getAll(request, name)` | 保留重复参数、空值等语义 |
| `pulse.query.set / append / remove` | 操作 URL 查询参数，提供明确的编码规则 |
| `pulse.cookies.get / set / remove` | 按 Cookie 语义处理；请求 Cookie 与响应 Set-Cookie 分开实现 |
| `pulse.body.text / setText` | 明确字符编码，文本转换失败返回可定位错误 |
| `pulse.body.json / setJSON` | 读取 JSON；写入时同步需要的内容元数据 |
| `pulse.body.bytes / setBytes` | 二进制读取与写入，避免 UTF-8 往返损坏 |
| `pulse.encoding.base64 / hex / utf8` | 明确字符串与字节输入输出；非法输入报告错误 |
| `pulse.crypto.sha256 / hmacSha256` | 先覆盖签名高频需求；输入编码和结果编码明确 |

设计要求：

- 保留 `ctx.request.headers` 数组、直接修改 URL/文本 Body 的快速写法。
- 帮助函数直接作用于同一个报文草稿，避免 raw 数据和封装对象出现两份独立状态。
- v2 的字节数据是 Body 的权威表示；兼容的 `.body` 文本访问通过宿主访问器转换，不同时保留两个互不关联的可写副本。
- 明确重复 Query 参数、`+` 与 `%20`、空值、无 `=` 参数及 `Set-Cookie` 的处理；不能为了“方便”把重复值全部压成普通对象。
- 提供便利的结构化模式，同时在进阶阶段提供受传输协议限制的 raw 操作模式，满足签名和非标准请求测试。
- Body 改动后统一处理 Content-Length、内容编码；URL 改动后统一处理目标地址与 Host。不能让插件作者手工修补所有传输细节。
- 对没有被编辑的部分尽量保留原始表示，避免解析再序列化破坏依赖原始字节的签名。

### 5.2 明确可读与可写字段

v2 应提供一张自动生成、可测试的字段表：

| 阶段 | 可以修改 | 只读数据 |
| --- | --- | --- |
| `onRequest` | method、url、headers、body | Flow 标识、来源、时间、实际传输能力 |
| `onResponse` | status、headers、body | 已发送的 request、原始关联标识 |
| `onComplete` | 插件结果、标签、插件存储 | 已完成事务的请求与响应 |
| Action | 动作自己的报文副本、结果、显式发起的新请求 | 用户选择的原始历史记录 |

`httpVersion` 不应导出成“赋值了却没用”的字段。HTTP 协议由传输层控制时，应标为只读；将来开放协议选择时，另设明确的发送选项。`reason` 应按 HTTP/1 与 HTTP/2 能力分别处理，不能承诺两者都有可改的 reason phrase。

响应阶段修改 request 的旧行为，在 v1 兼容路径保留并提示其局限；v2 拒绝误导性的写入。不要悄悄改变旧插件行为。

### 5.3 状态与持久化（R1）

| 状态 | API 草案 | 生命周期与用途 |
| --- | --- | --- |
| 单事务上下文 | `ctx.state` | 同一插件、同一 Flow 的 request/response 共享；事务结束释放 |
| 插件内存状态 | `pulse.store.memory` | 跨请求共享；适合 Token 缓存、去重、临时计数；重启释放 |
| 插件持久状态 | `pulse.store.local` | 插件命名空间下保存 JSON；重启保留 |
| 用户配置 | `ctx.config` | 每次调用使用配置快照；脚本不能隐式改写用户设置 |

关键约定：

- 不通过复用 VM 或全局变量偶然持久化状态；由宿主存储提供确定语义。
- `get()` 返回副本，`set()` 提交值，禁止跨 VM 共享 JS 对象。
- 内存状态支持 TTL；各存储提供 `get/set/delete/keys` 和明确的数量、大小限制。
- 提供原子的 `increment`、`compareAndSet` 等少量必要操作，避免并发请求下 `get → 改 → set` 丢更新。
- Token 刷新使用后续宿主 `singleFlight(key, task)` 合并并发工作；并发请求等待同一结果，等待受各自截止时间控制。
- 测试默认使用独立状态副本，允许清空、导入、连续运行多条用例，不污染运行中的插件状态。
- 插件停用时保留持久配置与状态；删除时由用户决定是否同时删除状态。清空状态是明确操作。
- 插件热更新保留宿主状态；运行中事务固定使用开始时的插件修订，避免 request 与 response 使用不兼容代码。

### 5.4 主动 HTTP 请求与异步能力（R2，核心能力）

建议提供 `pulse.http.send()`，优先支持重复 Header、字节 Body、超时、重定向策略和代理选择。命名为 HTTP API，避免暗示完整兼容浏览器 Fetch。

```js
// R2 API 草案：需先实现异步任务调度。
async function refreshToken(ctx) {
  const response = await pulse.http.send({
    method: "POST",
    url: ctx.config.refreshUrl,
    headers: [{ name: "Content-Type", value: "application/json" }],
    body: JSON.stringify({ refreshToken: ctx.config.refreshToken }),
    timeoutMs: 5000,
    redirects: "manual"
  });
  if (response.status !== 200) throw new Error("Token 刷新失败");
  const token = pulse.body.json(response).access_token;
  if (typeof token !== "string" || !token) throw new Error("响应缺少 access_token");
  return token;
}
```

行为必须具体：

- 每条主动请求记录 `source: plugin`、插件 ID、父任务/Flow ID，能在 Live Traffic 中查看和筛选。
- 默认绕过插件链、Match & Replace 和人工拦截，防止刷新 Token 再触发自身、或在拦截队列中死锁。
- 需要再次经过扩展时使用显式选项；继承执行链标识，限制递归深度并显示调用路径。
- 目标由插件配置或代码决定；首次使用网络能力时确认授权范围，之后不逐请求弹窗。
- 允许用户为可信插件选择任意 HTTP/HTTPS 目标，包括本地开发服务；不把合法使用统一限制成某个固定域名。
- 网络能力范围与自动执行范围分开：前者决定能访问哪里，后者决定哪些流量触发插件。
- 重定向逐跳检查授权；跨源跳转不自动携带 Authorization、Cookie 等凭证。
- 请求携带的 Cookie/认证信息必须显式来源，不自动继承浏览器或任意流量中的凭证。
- 脚本超时、取消或停用后应取消未完成 I/O，不留下继续运行的请求和回调。
- 不默认自动重试有副作用的请求；由插件明确选择重试策略。

goja 是 JS 引擎而不是 Node.js 宿主。官方文档说明同一 Runtime 不能被多个 goroutine 并发使用，计时器/事件循环需要宿主提供。因此异步能力必须包含受控调度、Promise 等待、取消传播和宿主 I/O 截止时间，不能只暴露一个 Go HTTP 函数后就宣称支持完整 async 插件。[goja 官方说明](https://github.com/dop251/goja)、[官方事件循环实现](https://github.com/dop251/goja_nodejs/blob/master/eventloop/eventloop.go)。

### 5.5 Mock、阻断与完成后分析（R2）

- `ctx.respond({ status, headers, body })`：在 request 阶段返回本地响应，不发送上游请求。它是本次钩子的终结动作，重复设置或与 drop 冲突时报告错误。
- `ctx.drop({ reason })`：明确终止当前事务，Flow 中标记为插件主动阻断，与运行错误区分。
- Mock 成功后仍进入正常响应插件/响应重写/响应拦截阶段；记录 `responseOrigin: plugin`，便于定位。drop 不再运行普通响应转换。
- `onComplete(ctx)`：对已结束事务执行只读分析、标签和结果输出。作为有界后台任务，不阻塞响应返回。
- 提供取消与队列满反馈；不可无限创建后台 goroutine 或不受管理的定时器。
- 队列满时显示丢弃/延迟统计；完整批量扫描应使用显式任务，而非假设每个高频回调永不丢失。

## 6. 手动执行与 Pulse 工作流联动

### 6.1 注册手动动作（R2）

在插件定义中声明 Action，宿主映射到流量右键菜单、报文工具栏、Repeater 菜单或命令入口。动作通过稳定 ID 关联函数。

动作可声明：

- 名称、说明、适用选择类型（请求、响应、选中文本、多条 Flow）。
- 是否支持多选，以及每次最多处理多少条。
- 参数表单，如环境、字典、解密密钥引用。
- 输出类型：文本、JSON、Diff、表格、二进制下载。

首批动作示例：`计算签名`、`解密响应`、`提取接口地址`、`复制自定义格式`、`发送到 Repeater`。

手动动作可以使用已安装但未开启自动钩子的插件；界面明确区分“已加载，可手动运行”和“自动处理已开启”。用户选择运行本身即为该次动作意图，不再弹一次普通确认；新增网络/文件能力授权在安装或首次需要时单独处理。

### 6.2 与 Repeater 联动

- 保留 Repeater 默认不自动经过插件的行为。
- 提供 `Apply plugin…`：对当前编辑请求的副本运行指定插件，先显示 Diff，再应用到编辑器，不立即发包。
- 手动动作允许显式发送请求，并在按钮上写清 `Run and send`。
- “发送时自动应用指定插件”作为后续按标签配置项，不设成所有 Repeater 标签的隐式全局行为。
- 如果插件已经发起真实请求，不再追加一层“仅预览”的误导文案。

### 6.3 查询与结果输出

提供分页、有限量的 `pulse.flows.query()` 与 `get()`；不得一次把整个流量库加载到 VM。查询结果默认只读，删除历史等操作不混入基础读取 API。

提供统一的 `pulse.results` 输出接口，并复用现有流量标记、备注和检查器能力：

- 结构化结果关联 Flow，可点击返回请求。
- 解密结果进入附加视图，不必改写客户端真实收到的响应。
- 批量动作显示进度、成功/失败数量、取消按钮和可导出的结果。
- 对 lean capture、正文被丢弃或截断的 Flow 显示数据不完整，不把占位正文当作完整样本。

## 7. 配置、能力与开发者控制

### 7.1 配置表单

`plugin.config` 声明 string、number、boolean、select、secret 等少量类型；宿主生成表单，展示默认值、说明、校验错误。

- 普通使用者修改 URL、Token、环境时不需要编辑源码。
- 配置保存使用修订号，运行时读取快照；无效配置不替换有效配置。
- secret 默认不回显、不随插件导出、不进入测试快照；日志格式化对已知 secret 值做基础脱敏，但不宣称能识别任意派生密钥。
- 密钥存储方式单独实现和说明，密码输入框不能被描述成“已加密存储”。支持平台凭据存储时明确支持范围。
- 配置复制与环境切换后续增加，先完成单份配置可靠读写。

### 7.2 能力授权

| 能力 | 推荐处理 |
| --- | --- |
| 修改当前报文、标准编码、基础日志 | 基础能力，启用插件即可使用 |
| 插件自己的状态与存储 | 默认可用，命名空间隔离并有可见容量限制 |
| 主动 HTTP 请求 | 显示网络能力，可选择目标范围或可信插件的全部 HTTP/HTTPS 目标 |
| 读取历史流量、创建手动动作 | 安装/更新时展示用途，操作过程不逐项弹窗 |
| 读取/写入本地文件 | 用户授予具体目录；UI 明确是 Pulse 服务所在机器的目录 |
| 调用外部进程 | 后续可信模式，明确可执行程序和参数边界，通过独立执行进程管理 |

原则是**把能力边界交给用户一次配置，把日常编程自由交给开发者**。不在每次 Hook、每条流量或每次状态读取时重复询问。

权限扩大时单独确认新增能力；普通源码修改和权限不变的更新不反复打断。拒绝新增能力时，上一有效版本继续工作。

### 8.2 编辑器

- 复用现有 CodeMirror，补齐撤销/重做、查找替换、括号/引号补全、缩进和代码折叠。
- 提供 `ctx`、`pulse`、Hook 名称、配置键的补全与悬浮说明；先提供宿主 SDK 的确定补全，不承诺完整 TypeScript 语言服务器。
- Check 返回结构化诊断：文件、行、列、错误代码和消息；点诊断定位代码，不仅在顶部显示长字符串。
- SDK 帮助作为可展开侧面板，展示字段是否只读、返回类型、可用阶段与最小示例。
- 行号、错误标记、当前行保持清晰，主题复用已有变量。
- 网络操作不锁住编辑器；Check/Test/Save/Apply 分别显示自己的执行状态，不共用一个全局 busy 冻结全部动作。
- 请求结果按源码与样本修订号归属，迟到的旧结果不能覆盖新代码对应的结果。
- `Ctrl/Cmd+S` 保存源文件；`Ctrl/Cmd+Enter` 在插件编辑区运行测试；Apply 保持独立显式按钮，避免误把保存当成运行部署。

### 8.3 草稿、源文件、运行版本

本提案对上一轮“Ctrl+S 只保存本地草稿”的建议作调整：**遵循开发者习惯，Ctrl+S 保存源文件，Apply 才更新运行版本；草稿由系统自动保存。**

| 状态 | 展示与行为 |
| --- | --- |
| 正在编辑 | 文件名后显示未保存标记；约 500ms 防抖保存本地草稿 |
| 草稿已保存 | 显示 Draft saved；不是源文件写盘成功 |
| 源文件已保存 | 显示 Source saved；若不同于运行修订，同时显示 Unapplied changes |
| 应用中 | Apply 显示进度，编辑仍可继续；应用绑定点击时的源码快照 |
| 应用成功 | 显示运行修订和自动处理状态；不清除应用期间新写的内容 |
| 应用失败 | 保留源文件和诊断，旧运行版本继续工作 |
| 自动处理关闭 | 明确显示 Auto hooks off；若插件加载正常，允许手动动作和测试 |
| 外部文件变化 | 若无本地修改可重新读取；有冲突则提供对比，不直接覆盖 |

运行修订应独立存储有效源码/产物及配置引用，并能在重启后恢复。仅在内存里保留旧 `goja.Program` 不足以实现“坏源码保存后重启仍可用”。

第一版只保留当前与上一有效运行修订，支持一键回退；不开发完整 Git 版本管理。回退默认只回退代码，不隐式回退用户状态和密钥配置。

本地草稿按服务实例、插件 ID 和文件路径分键；存储失败时提示未保护，不能谎报已保存。测试样本可能包含凭证，显式保存为用例时允许去敏；普通源码草稿与真实流量样本分别管理。

### 8.4 测试台

输入来源：当前 Flow、Repeater 编辑缓冲区、粘贴 raw、手写 JSON、已保存测试用例。

执行模式：

- `Request`：只运行请求钩子。
- `Response`：提供关联请求与响应，只运行响应钩子。
- `Transaction`：以提供的请求和响应样本运行两个阶段，并验证 `ctx.state` 传递；不会推断真实上游会如何响应修改后的请求。
- `Action`：模拟选中项和参数，执行手动动作。

结果区提供 `Diff / Output / Logs / Assertions`。顶部显示：通过、失败、无修改、已过期、取消，以及耗时；“执行成功但无修改”属于正常结果，不显示错误。

R1 先支持几类可视化断言：Header 值、URL、状态码、JSON 字段、正文包含/不包含、未修改。断言在隔离输入输出上运行，不写入生产状态。

R2 网络能力上线时，必须同时提供：

- 默认 Mock 网络，未配置的请求直接报 `unmocked network request`，不悄悄放行到真实网络。
- 用例中声明 Mock 响应、超时和失败，便于测试 Token 刷新。
- 明确的 `Live test` 模式，使用已授予的网络能力；界面持续显示真实网络模式。
- 每次测试使用自己的状态副本与运行 ID；停止测试能取消代码和 I/O。
- 从历史记录导入的报文标注为“已存储报文”，若此前已被插件修改，不冒充原始输入。

### 8.5 运行记录与可观测性

- 列表只显示运行健康摘要；详细日志与记录在 Activity 加载。
- 结构化日志包含时间、级别、插件 ID、修订、执行 ID、Hook/Action、Flow ID、消息。
- 每次记录区分：已跳过、成功无修改、成功有修改、错误、超时、主动阻断、取消。
- 自动跳过的每条流量不必存完整记录；以计数汇总，调试模式再展开原因。
- 错误记录保留到历史中，不被下一次成功抹掉；列表可以显示最近错误和当前恢复状态。
- 对日志暂停滚动，用户在查看旧日志时不强制跳底；支持复制当前执行日志。
- 第一版采用有界内存记录，建议每插件最近 100 次执行摘要、全局最近 1000 次；正文默认不进入摘要。具体容量通过实际流量验证后调整。
- 完整输入输出仅在调试记录开启时保留，设置字节上限并标注截断；不与普通计数绑定。
- SSE 若复用应合并高频统计更新；短期保留 4 秒轮询时，隐藏页面暂停、失败标过期、避免重叠请求和旧响应覆盖新状态。

### 8.6 样例与空状态

Templates 用“任务”命名，优先包含：

1. Add authentication header。
2. Capture token from login response。
3. Sign request with HMAC。
4. Rewrite JSON request/response。
5. Mock API response。
6. Decode selected response。
7. Refresh token with HTTP request。
8. Extract endpoints from selected flows。

每个模板包含简短用途、所需能力、配置字段、测试输入与期望输出。点击 `Use template` 创建新副本并进入编辑，不覆盖正在写的插件，不立即开启自动处理。

首屏提供 `New plugin`、`Use template`、`Import`，而不是只提示“去其他标签页找样例”。

## 9. 执行规则与运行时实现

### 9.1 自动触发范围和顺序

- 允许选择全部代理流量、当前 Scope、指定 Host/路径/方法；高级用户可以选择全部流量并完全在代码里判断。
- 新建自 Flow 的插件默认限定该 Host；空 Scope 不解释成全部流量。
- 旧插件迁移保留原本自动处理范围，不能静默缩小或扩大。
- 运行来源默认 proxy；Repeater、插件主动请求、后台任务分别明确选择。
- UI 按真实执行顺序显示；上移/下移是基础操作，拖拽是增强操作。
- request 与 response 默认沿用同一顺序，避免引入隐式逆序；有实际需求再提供分阶段排序。
- 先判断范围再创建 VM；初始化和计算只发生在需要执行的插件上。
- 范围匹配默认依据进入扩展链时的请求快照，防止前一插件改 Host 后意外激活另一站点插件；脚本仍能读取前序修改后的当前报文。
- 一次事务固定插件列表、顺序、修订和配置快照。停用后不再接收新自动调用；尚未启动的阶段跳过已停用插件，正在执行的任务遵循取消策略。

### 9.2 错误与提交语义

- 每个转换钩子在当前报文的副本上执行，成功后验证并一次提交；抛错或超时不提交半成品报文。
- 默认继续使用该插件执行前的报文并运行后续插件；该默认策略在 UI 和文档中可见。
- 对鉴权/签名等不能接受失败后继续发送的场景，允许用户按插件选择“失败时终止事务”。不要把一种错误策略强加给所有插件。
- 日志、网络请求、外部文件写入不能随报文回滚；状态写入也不是跨 API 的事务。文档明确副作用边界，返回结构化错误与已发生副作用摘要。
- 默认不因一次错误永久停用插件；连续超时/错误可以触发用户可配置的暂停策略，显示触发原因与恢复按钮。

### 9.3 预算与取消

- 区分同步流量钩子与用户主动运行的任务。钩子沿用短预算起步；手动分析/批量任务允许更长预算和独立队列。
- 每个插件可配置预算，宿主给出上限与当前值；不要把所有解密、网络、批量任务统一锁死在 2 秒。
- `vm.Interrupt` 覆盖顶层执行和钩子，宿主 HTTP/文件/进程操作通过独立取消上下文中断。
- 异步任务只有在 Promise 结算或截止时间到达后才结束；迟到的回调不能提交结果或写入新的运行修订。
- 同一 VM 由单一执行调度上下文拥有，I/O 完成后投递回该上下文；Go goroutine 不能直接并发操作 goja 值。
- 输出、日志、状态、网络响应、任务队列均有可见容量上限，超过限制返回错误或明确截断标记。
- goja 的进程内 VM 隔离不等于操作系统级内存隔离，超时也不等于内存上限。需要强制内存限制或高权限本地代码时，应使用独立执行进程。
- 不为“性能优化”直接复用有残留全局状态的 VM；优先编译缓存、范围预过滤、减少对象复制，再依据压测决定是否扩展执行架构。

### 9.4 生命周期函数

R2 再引入 `onLoad`、`onUnload` 等生命周期：

- 顶层代码只负责定义元数据、函数与声明；Check 不应触发网络或文件副作用。
- Check 的临时 VM 只暴露校验所需的受限能力；真正可产生外部副作用的宿主方法在校验阶段拒绝执行。
- `onLoad` 在运行修订准备好时执行，用于初始化宿主状态；应用流程显示其结果。
- `onUnload` 为有限时间的尽力清理，不能阻止退出；状态不能依赖它才写盘。
- 生命周期钩子和每次调用的新 VM 是不同概念，初始化结果通过宿主状态传递。

- manifest 声明入口产物、API 版本、元数据、能力与测试清单；单文件仍使用代码中的 `plugin` 元数据。
- 项目形式的元数据以 manifest 为权威来源，构建时校验代码声明是否冲突，避免两套配置互相覆盖。
- 开发者可以使用自己的编辑器、Git、TypeScript 和构建工具，Pulse 消费已构建的 JS 产物。
- 先支持打包为单文件的纯 JS 依赖，提供模板和明确编译目标；不承诺未实现的原生 ESM 加载器。
- TypeScript 通过外部构建为 JS；浏览器编辑器先服务 JS，不把完整 TS 编译链作为单文件使用门槛。
- npm 依赖在开发机安装与打包，Pulse 运行时无需访问包仓库；导入插件不自动执行 npm install 或安装脚本。
- 提供 SDK `.d.ts`、示例、Source Map 错误定位和命令行检查/试跑入口；浏览器与 CLI 调用同一宿主契约。
- 基于仓库锁定的 goja 版本验证语法、Promise、TypedArray 和打包产物兼容性，发布兼容矩阵，不笼统写“完整 ES202x / Node 兼容”。

### 10.2 文件热更新

- 内置编辑器保存和外部文件更新均进入相同的候选版本流程。
- 用户可开启 `Auto apply valid changes` 开发模式；默认显式 Apply。
- 文件保存触发防抖，先构建/校验，成功后原子切换；失败保留旧运行版本。
- 界面显示变化来源、应用时间、当前运行修订与错误，不只提供“Reload 成功”。
- 外部删除文件时显示 Source missing，保留运行修订但不悄悄重新创建源码；由用户明确恢复、停用或移除。

### 10.3 自定义 UI

分两层开放：

1. **R2 标准结果 UI**：文本、JSON、Diff、表格、下载，满足大部分解密和分析插件。
2. **R3 自定义面板**：允许插件提供 HTML/JS 产物，通过受隔离的 iframe 和版本化消息桥与后端交互；保留组件框架选择自由。

不把插件脚本直接注入 Pulse React 页面或授予任意 DOM 访问。自定义面板通过明确的桥接 API 获取选择、调用后端动作、导航到 Flow、读取主题与输出结果。

宿主校验每条桥接消息的插件身份、目标实例、消息结构和允许的方法；隔离面板不直接获得控制台管理凭证。代码加载、CSP、外部网络与跨窗口通信策略在该阶段单独设计并测试。

开放位置优先级：报文检查器附加页签 → 插件详情自定义页 → 独立侧栏页。避免第一版就开放任意位置注入。

Caido 的 SDK 将后端请求能力与前端菜单、面板等能力分开，可借鉴其“能力分层”的方向；Pulse 的具体 API 保持轻量和本地运行定位。[Caido SDK 参考](https://developer.caido.io/plugins/reference/)、[前端 SDK](https://developer.caido.io/plugins/reference/sdks/frontend/)。

### 10.4 本地资源与进阶执行模式

- Files API 从用户授予的目录中读写字典、插件数据与结果；路径规范化、符号链接、Windows junction、读写权限必须实际校验。
- 内置样例/只读资源可随插件打包，读取打包资源不要求用户额外选择系统目录。
- 需要外部工具时允许显式进程调用，提供参数数组、工作目录、环境变量选择、超时和输出限制，不默认经 shell 拼接命令。
- 引入高权限执行之前，先具备独立进程的停止、崩溃恢复和资源控制。可评估由同一个 Pulse 二进制启动 worker 模式，维持单文件交付。
- 文件与进程属于进阶阶段，不以扩大权限为理由阻塞报文助手、状态和 HTTP 请求这些核心能力。

## 11. 接口与前后端拆分建议

### 11.1 REST 契约草案

现有接口保留兼容；新增语义通过独立路径或明确 API 版本承载，不能直接改变旧 PUT 的行为。

| 接口草案 | 用途 |
| --- | --- |
| `GET /api/plugins` | 元数据、自动启用状态、加载健康度、源码/运行修订摘要；不每次附带所有日志 |
| `PUT /api/plugins/{id}/source` | 保存候选源码，携带 expectedRevision 防止外部修改被覆盖；不激活 |
| `POST /api/plugins/{id}/check` | 编译与结构化诊断，不更新运行版本 |
| `POST /api/plugins/{id}/apply` | 应用指定源码修订与配置修订，成功后切换运行版本 |
| `POST /api/plugins/{id}/rollback` | 恢复上一有效运行修订 |
| `GET/PUT /api/plugins/{id}/config` | 配置读写与字段校验；secret 返回是否已配置而非明文 |
| `GET/PUT /api/plugins/{id}/execution` | 自动触发范围、来源、顺序与预算 |
| `POST /api/plugins/{id}/tests/run` | 运行指定修订、样本和模式，返回执行 ID |
| `GET /api/plugins/{id}/runs` | 有界分页读取执行记录 |
| `POST /api/plugins/{id}/runs/{runId}/cancel` | 取消测试、手动或后台任务 |
| `POST /api/plugins/{id}/actions/{actionId}/run` | 使用明确选择和参数运行 Action |

Apply 返回值至少包含插件 ID、应用修订、自动启用状态、加载结果；不能只返回 `ok: true`。网络错误、JS 错误、超时、配置错误分别有稳定错误代码，前端据此定位到正确区域。

未安装草稿的校验/测试继续复用现有接收源码的端点，扩展为同一运行结果结构；不要要求用户必须先安装插件才允许试跑。

### 11.2 前端组织

建议把现有单个 ExtensionsView 中的插件功能按真实职责逐步拆分：

- `PluginsWorkspace`：选中插件、页签、路由和布局。
- `PluginList`：列表、过滤、健康摘要、自动启停。
- `PluginEditor`：源码、草稿、诊断、保存与应用。
- `PluginTestPanel`：样本来源、模式、运行结果、断言。
- `PluginConfigPanel`：配置表单与校验。
- `PluginExecutionPanel`：范围、来源、顺序、预算。
- `PluginActivityPanel`：日志和执行记录。

这些是后续拟新增职责，不要求一次创建全部空组件。先复用现有 CodeEditor、Split、DiffView、MessageViewer、ContextMenu 和 Confirm。SDK 的补全、诊断、类型定义由同一份契约生成或校验，避免前端提示与后端支持再次不一致。

### 11.3 后端组织

先在 `internal/plugins` 内按执行、报文、状态、HTTP、版本与记录拆文件，不为每个文件引入接口或工厂。仅当独立 worker / 自定义面板确有需要时，再引入进程通信或桥接层。

代理链路、Repeater 显式应用、沙箱测试和 Action 必须复用同一报文转换逻辑。预览环境用可替换的网络和存储实现隔离副作用，不能维护一套与生产行为不同的“假执行器”。

## 13. 验收与验证计划

### 13.1 产品验收

1. 初次使用者通过模板创建“目标 API 鉴权头”插件，配置 Token、导入一条真实请求、看到 Diff，再启用；无须手写测试 JSON。
2. 开发者从登录响应提取 Token，后续请求成功使用；并发下状态行为明确，重启后的持久状态符合配置。
3. 坏代码保存、Check 或 Apply 失败后，当前有效插件仍可运行，重启仍恢复该有效版本。
4. 停用自动钩子后仍可手动测试或执行已加载动作；界面不会显示互相矛盾的“停用/不可运行”。
5. 修改源码或测试输入后，旧结果标记过期；运行中的旧测试返回不覆盖新结果。
6. 网络插件在默认测试模式下不能发出真实请求；切换 Live test 后可以使用已授权能力并停止任务。
7. 用户从一条被修改的 Flow 能找到插件、修订、执行阶段和错误信息。
8. 复杂插件可以使用外部编辑器、类型提示与纯 JS 依赖打包，不依赖在线编辑器完成全部开发。

### 13.2 后端测试

- 旧单文件插件加载与执行兼容；v2 只读字段、重复 Header、URL 编码、Cookie、多字节与二进制 Body 行为。
- 顶层死循环、Hook 死循环、Promise 永不完成、网络超时、取消期间返回、无效报文写入。
- 并发状态更新、TTL、Token 刷新合并、跨插件隔离、跨事务关联、插件停用和热更新中途的行为。
- 候选源码保存失败、状态持久化失败、应用失败、版本回退、重启恢复、目录切换与身份冲突。
- 网络重定向、凭证传递、插件自调用、递归深度、响应体超限、队列满、后台分析不阻塞主响应。
- 每个模板使用与 UI 同源的源码和用例，防止样例与 SDK 漂移。

### 13.3 前端与真实操作

- 自动化覆盖草稿恢复、保存/应用状态、旧响应竞争、诊断定位、样例不覆盖、取消、表单错误与空状态。
- Windows 浏览器实际操作完整走通创建 → 配置 → 测试 → 应用 → 发起受控流量 → 查看记录 → 停用 → 回退。
- 在 1280×720、1440×900 和更宽窗口检查工作区；三套主题、分栏拖拽、键盘导航、减少动态效果均要检查。
- macOS 行为在对应平台单独验证，不用 Windows 结果替代；界面预览也不替代原生或文件权限测试。
- 审查性能时对比无插件、空插件、典型签名插件、网络插件，记录新增延迟、并发行为和内存；先建立基线，再确定回归阈值。
